# Gotchas

See [[architecture]] for the pieces involved.

- **Database must be Neon.** `backend/src/drizzle/db.ts` uses `drizzle-orm/neon-http`. A Supabase or plain Postgres URL will not work. Create tables with `yarn db:push` in `backend/` (reads `backend/.env`).
- **AI keys are optional on the server now.** `OPENAI_API_KEY` and `GEMINI_API_KEY` in `backend/.env` are only a shared fallback; users can save their own in Profile. With neither, chat returns `API_KEY_MISSING` (HTTP 400, or an SSE error) telling the user to add a key.
- **`KEY_ENCRYPTION_SECRET` is required to save keys** (generate with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`). Without it, `PUT /api/keys/:provider` returns 503 and the Profile card says saving is not set up. Changing it makes every saved key undecryptable, so users would have to re-enter them. `SKIP_KEY_VERIFY=1` skips the provider check when saving (tests only).
- **The agent dialog's built-in model list is hard-coded** (`PROVIDERS` in `frontend/lib/providers.ts`; names checked against provider docs on 2026-11-05, and the DeepSeek flash id was reported two ways, `deepseek-flash` and `deepseek-v4-flash`) and goes stale; it is only the fallback when the live list is unavailable (no key, provider error). The live-list path was tested with fixture data and the endpoint's fallbacks, not with a real provider key.
- **`EMAIL_FROM` is required for emails** (used as the sender in `emailService.ts`) and was missing from `.env.example` until 2026-11-03. SMTP defaults are Gmail (`smtp.gmail.com`, 587); `SMTP_PASSWORD` must be a Google app password.
- **CORS origin has two names:** `app.ts` reads `CLIENT_URL`, `config.ts` reads `CORS_ORIGIN`. Set both to the frontend's address.
- **Local ports:** backend 4000. The frontend defaults to 3000, which can clash with another app; use `next dev -p 3001` and set `CLIENT_URL` and `CORS_ORIGIN` to match.
- **The frontend has no production default any more.** Copy `frontend/.env.example` to `frontend/.env.local`; with nothing set it proxies to `http://localhost:4000`. Restart `next dev` after changing `next.config.mjs` or env.
- **Backend logs are untracked** (since 2026-11-03; `backend/.gitignore` ignores `logs/` and `*.log`). They are still written to `backend/logs/` while the server runs.
- **Two lockfiles in `frontend/`:** `yarn.lock` is real; `pnpm-lock.yaml` is a stub. Use yarn.
- **No ESLint config in either package,** so `eslint` has nothing to run. Use `npx tsc --noEmit`.
- **Application Control blocks `graphify.exe` on this machine.** Run `python -m graphify update .` instead (approved by the author). Graphify skips `.sql` files until `pip install "graphifyy[sql]"`.
- **The app screens need a login and the backend,** so visual checks of agents, chat, analytics and profile need both running.
- **`liquid-glass-react` sizes itself from its content and centres itself in its parent** (top/left 50% with a -50% transform). Percentage-width content measures as zero and the lens collapses. Use the `Lens` wrapper (`components/glass-lens.tsx`): it measures its box and gives the library pixel sizes, so a lens needs a known height. Safari and Firefox show the frost but not the bend. Keep lenses to a few surfaces; each one is an SVG filter.
- **Reduced motion and the lens squish were not tested in a browser** (the code uses `useReducedMotion`).
- **The route-transition wrapper in `app/app/client-layout.tsx` must be `h-full`, not `min-h-full`.** The chat and agents pages size themselves with `h-full`; under a `min-h-full` parent their height collapses (the chat looked like it did not fill the screen).
- **Do not give a page wrapper an opaque background** (`bg-background` and similar): the glass look relies on the fixed `Backdrop` (`components/backdrop.tsx`, in the root layout) showing through, and an opaque wrapper hides it so glass panels look flat. Use `Panel` for calm surfaces and `GlassPanel` or `.glass` for glass.
- **Agent `model` is not whitelisted.** `validation.ts` only checks the id's shape, because the dialog offers each provider's live list. It used to be a fixed list that would have rejected newer models.
- **OpenAI GPT-5 and later, and o-series, get `max_completion_tokens` and no `temperature`** (`chatParams` in `llmService.ts`); DeepSeek and older models get `max_tokens` and `temperature`. Not yet confirmed against a real key.
- **Radix Select can emit an empty value when its option list changes.** The model select ignores empty values and renders the selected name itself (otherwise it showed the placeholder after switching provider).
- **Forms inside a `ScrollArea` need a few pixels of side padding.** The scroll viewport clips overflow, so a focus ring on a full-width field is cut at the edges (the agent dialog form uses `px-1 pt-1`; not yet re-checked in the browser).
- **Toasts come from Sonner, mounted once in `app/layout.tsx`** and styled there with `toastOptions.classNames` using the app tokens (`--popover`, `--glass-edge`). `components/ui/sonner.tsx` and `components/ui/toaster.tsx` (a different, older toast) are not what the app's `toast()` calls show. Not yet checked in the browser.
- **The agents page's opaque loading cover must only show on the first load** (`isFetchingAgents && agents.length === 0`). Opening Edit fetches the agent's details, and covering the page for that looked like a black flash. Not yet re-checked in the browser.
- **`errorHandler` needs four parameters** (`_next` is unused) or Express ignores it. Fixed 2026-11-05; malformed JSON now returns a JSON 400 instead of HTML.
- **After editing `globals.css` the dev server can keep serving the old stylesheet.** If a new class or variable has no effect, check the served CSS and restart `next dev` (the chat code colours looked broken until it was restarted).
- **Persisted-store data causes hydration mismatches** unless shown after mount (profile page uses a `mounted` flag).
- **Agent cards enter with `motion`, not a CSS `animate-in` with `fill-mode: both` on a `transition-all` element.** After going Chat to Agents the cards could stay faint until hovered; I could not reproduce it here, so the cause is a best guess (CSS animation and transition fighting over opacity) and the check is still open.
- **Cookie auth needs `X-Requested-With: nebula` on anything but GET** (axios sets it; the chat stream sets it by hand). Without it `authenticate` answers 403. A `Bearer` header is still accepted for tools.
- **The live-metrics socket gets a one-minute token from `GET /auth/socket-token`** (`lib/metrics-socket.ts`), because the cookie is not sent to the socket server.
- **Browser calls go to same-origin `/api`, which `next.config.mjs` rewrites to `BACKEND_URL`.** That keeps the login cookie first-party when the frontend (Vercel) and API (Render, later a home server) have different domains. Changing the backend host is one env var. The chat stream and the live-metrics socket cannot use the proxy (long streams, websockets), so they go straight to `NEXT_PUBLIC_DIRECT_API_URL` with a one-minute token from `/auth/socket-token`; that is why `CLIENT_URL` on the backend must be the exact frontend URL (CORS). Tested locally; not yet on Vercel/Render.
- **Behind Vercel and Render, set `TRUST_PROXY=2` on the backend** or the rate limiter counts every visitor as one (they all arrive from Vercel). Use the real number of proxies; too high lets visitors fake their address.
- **Production env:** Vercel: `BACKEND_URL` (the Render URL, no `/api`), `NEXT_PUBLIC_DIRECT_API_URL` (Render URL plus `/api`). Render: `CLIENT_URL` (the Vercel URL), `TRUST_PROXY=2`, `NODE_ENV=production`, `KEY_ENCRYPTION_SECRET`, the JWT secrets and database URL. Leave `COOKIE_SAMESITE` as `lax`.
- **The one-minute ticket (`/auth/socket-token`) carries `purpose: "ticket"`** and `authenticate` accepts it only for `POST /api/chat/:id/stream`; the metrics socket accepts only tickets. A stolen ticket cannot read data or change a password. Checked with curl (401 on profile and agents, works on the stream).
- **The login is two HttpOnly cookies, nothing in `localStorage`.** `nebula_session` is a 15-minute access token (`JWT_EXPIRES_IN`; this machine's `.env` was set to 15m on 2026-11-05, and Render must be set the same, since it used to be days). `nebula_refresh` is a random token (only its SHA-256 is stored in the `refresh_tokens` table) with cookie path `/api/auth`. The page only ever learns `expiresAt`, the end of the whole sign-in, kept in memory in `lib/session.ts` and restored by `GET /auth/profile` after a reload.
- **Silent refresh:** a 401 in `lib/store/api.ts` triggers one shared `POST /auth/refresh`, then the request is repeated. Only if that fails does `SessionGuard` show "Your session has ended" (or go to sign-in if nobody was signed in). Refresh tokens rotate: each works once; reusing an old one after 10 seconds ends the whole sign-in (10 seconds covers two tabs racing). Tested with a 20-second access token.
- **Remember me:** unticked, the refresh cookie is a session cookie and the server ends the sign-in after `SESSION_DAYS` (1); ticked, it lasts `SESSION_REMEMBER_DAYS` (30). The sign-in end is absolute, not extended by use.
- **Logout, password reset and password change end sign-ins on the server** (logout the current one; reset all; change all but the current one). The old weak spot (a copied token staying valid for days) is now limited to the 15-minute access token.
- **The `refresh_tokens` table was created by hand with SQL in the dev Neon database** (the schema is in `drizzle/schema.ts`). A new database needs `yarn db:push`. `JWT_REFRESH_SECRET` and `JWT_REFRESH_EXPIRES_IN` are no longer used but `JWT_REFRESH_SECRET` is still required at startup.
- **`render.yaml` (repo root) is the Render blueprint for the API** (root `backend`, build `yarn install --frozen-lockfile --production=false && yarn build`, start `yarn start`, health `/health`, non-secret settings filled in, secrets left for the dashboard). Both production builds passed on 2026-11-05. The old Render service `nebula-g9er.onrender.com` belonged to accounts the author lost, so a new service is needed. There is no Vercel project for Nebula yet; the frontend must be created with root directory `frontend`.
